# ctx harness

Wire ctx into an AI coding harness (Claude Code or Codex).

## Synopsis

```bash
ctx harness init [--target claude|codex] [--mode local|plugin] [--force] [--json]
ctx harness compat --require <SEMVER>
ctx harness doctor [--json]
```

## Description

`ctx harness` connects the ctx quality suite to an AI coding harness. The supported targets are Claude Code (`--target claude`, the default) and Codex (`--target codex`). An unknown target exits 2 and lists the supported values.

## Codex

`ctx harness init --target codex` writes trusted-project lifecycle configuration to
`.codex/hooks.json`, scripts under `.codex/hooks/ctx/`, and the shared starter
`.ctx/rules.toml`. It prints a guidance block for you to add to `AGENTS.md`.
Review and trust new or changed hook definitions with `/hooks` before you rely on them.

`ctx harness init --target codex --mode plugin` creates a distributable Codex plugin
with `.codex-plugin/plugin.json`, lifecycle hooks, the ctx skill, an optional MCP
configuration, and `.agents/plugins/marketplace.json` for local installation.

Everything `init` writes comes from templates embedded in the ctx binary. Every generated file carries a header:

```text
# generated by ctx v0.4.0 — regenerate with 'ctx harness init'
# ctx:checksum sha256:<hex>
```

The checksum makes regeneration safe. On a re-run, ctx regenerates files that still match their recorded checksum and skips, with a warning, files you modified or that ctx never generated. `--force` overwrites them. JSON files cannot carry comments, so ctx tracks them in a manifest, `.ctx/harness.lock`, instead.

Two files get special treatment:

- ctx never overwrites `.ctx/rules.toml` once it exists, not even with `--force`, because it holds your policy.
- ctx never edits `.claude/settings.json`. `init` prints a snippet for you to merge by hand.

## `init --mode local` (default)

Sets up the current project's `.claude/` directory:

| File | Purpose |
|------|---------|
| `.claude/hooks/ctx/session-start.sh` | `SessionStart` hook: prints `ctx map --budget 2000` for the model |
| `.claude/hooks/ctx/post-tool-use.sh` | `PostToolUse` (Edit\|Write) hook: `ctx index`, then `ctx check --against HEAD --json` |
| `.claude/hooks/ctx/stop.sh` | `Stop` hook: `ctx score --against <default branch>` scorecard (non-blocking by default, see [Blocking gates](#blocking-gates-ctx_gate_blocking)) |
| `.ctx/rules.toml` | Commented starter rules file (only when absent) |
| `.ctx/harness.lock` | Manifest of generated files and their checksums |

It then prints two blocks to stdout (instructions go to stderr):

1. A settings snippet to merge into `.claude/settings.json`: hook wiring plus a permissions block that allows `Bash(ctx *)` and denies `Bash(ctx self-update*)`, `Edit(.ctx/rules.toml)`, `Edit(.claude/hooks/ctx/**)`, and `Edit(.claude/settings.json)`.
2. A guidance block for your `CLAUDE.md` that tells the model to use ctx.

## `init --mode plugin`

Creates a distributable Claude Code plugin in the current directory:

| File | Purpose |
|------|---------|
| `.claude-plugin/plugin.json` | Plugin manifest (`version` = the generating ctx version) |
| `.claude-plugin/marketplace.json` | Local marketplace (`ctx-local`) for manual installs |
| `hooks/hooks.json` | Hook wiring via `${CLAUDE_PLUGIN_ROOT}` |
| `hooks/*.sh` | The same three hook scripts as local mode |
| `settings.json` | The permissions block (allow/deny above) |
| `skills/ctx/SKILL.md` | Skill teaching the model the ctx workflow |
| `README.md` | Manual install walkthrough (`/plugin marketplace add ./`, `/plugin install ctx@ctx-local`) |
| `.mcp.json` | MCP server wiring (`ctx serve --mcp`), only when this binary was built with the `mcp` feature. Otherwise a stderr note explains how to enable it |

## Hook behavior (fail open, with a warning)

Every generated hook script starts with a compatibility guard:

```sh
ctx harness compat --require "<version baked at generation>"
```

If the installed binary is older than the templates (exit code 3), the script prints a warning to stderr and exits 0 without doing its work. The session is not blocked, and the warning says why. Content for the model (map, check JSON, scorecard) goes to stdout. Notices for people always go to stderr.

## Blocking gates (`CTX_GATE_BLOCKING`)

The generated Stop hook runs `ctx score --against <default branch> --fail-on "check_violations>0"`. Duplication stays visible in the scorecard, but it does not fail the gate until you calibrate the heuristic against your repository. By default a failed gate only prints the scorecard and a stderr note, and the session stops normally. Set `CTX_GATE_BLOCKING=1` (exactly `1`) in the environment Claude Code runs in to make gate failures block the stop. The hook then exits 2, which Claude Code treats as "keep working", so the session continues until the failed conditions in the scorecard are fixed.

If you customize a Stop hook to include `new_duplication` while blocking mode is on, `ctx harness init` and `ctx harness doctor` warn you before that heuristic can hold a session open. To adopt it, first run `ctx score --against <default branch>` without a gate, review repeated findings in the scorecard, and only then add a calibrated duplication threshold to a blocking gate.

Only a real gate failure blocks. Everything else fails open:

| `ctx score` result | `CTX_GATE_BLOCKING` | Hook exit | Effect |
|--------------------|---------------------|-----------|--------|
| Gates pass (exit 0) | any | 0 | Session stops normally |
| Gate condition fired (exit 1) | unset / anything but `1` | 0 | Non-blocking; a stderr note points at the scorecard |
| Gate condition fired (exit 1) | `1` | 2 | Blocking stop; Claude keeps working on the findings |
| Operational error (exit 2, compat mismatch, ctx not on PATH) | any | 0 | Fail open with a stderr warning |

Pair it with `CTX_GATE_LOG` (read by `ctx score` itself, not the hook) to record every gate evaluation, including whether blocking mode was on, in a local JSONL log. See [ctx score: gate logging](./score.md#gate-logging).

> Upgrading: hook scripts are generated files. If your `.claude/hooks/ctx/stop.sh` predates the current gate defaults, re-run `ctx harness init` after updating ctx to regenerate it. The `templates_stale` check in `ctx harness doctor` tells you when this is due.

## `compat --require <SEMVER>`

Exits 0 when the running binary satisfies the requirement. Otherwise it prints one line to stderr and exits 3, a code only this subcommand uses.

A bare version (`0.2`, `0.2.1`) is a floor: the binary must be at least that version. ctx parses an expression with operators (`^0.2`, `>=0.2, <0.4`, `0.2.*`) as a full semver requirement. Input it cannot parse is an operational error (exit 2), never 3.

## `doctor`

Runs independent checks and reports findings (`error`, `warning`, `info`):

| Code | Checks |
|------|--------|
| `binary_version` | ctx version and whether the `mcp` feature is compiled in (info) |
| `harness_not_initialized` | nothing scaffolded yet (info) |
| `templates_stale` | generated files come from a different ctx version |
| `index_missing` / `index_schema` / `index_stale` | index existence, schema version, freshness vs file mtimes |
| `rules_missing` (info) / `rules_invalid` | `.ctx/rules.toml` presence and validity |
| `hooks_missing` / `hooks_modified` | generated hook scripts exist and match their checksums |
| `settings_not_wired` | `.claude/settings.json` does not reference `.claude/hooks/ctx/` |
| `mcp_unavailable` / `mcp_not_wired` | `.mcp.json` vs the binary's `mcp` feature |

Checks are independent: a missing index and an invalid rules file are both reported in the same run.

## Exit codes

| Code | Meaning |
|------|---------|
| 0 | Success (`init`), requirement satisfied (`compat`), healthy (`doctor`) |
| 1 | `doctor` found problems (errors or warnings) |
| 2 | Operational error (unknown `--target`, bad arguments, IO failure) |
| 3 | Version requirement not met (only `harness compat` uses this code) |

## Examples

### Wire ctx into Claude Code

```bash
ctx harness init
# merge the printed snippet into .claude/settings.json,
# add the printed block to CLAUDE.md, then:
ctx harness doctor
```

### Build a distributable plugin

```bash
mkdir ctx-plugin && cd ctx-plugin
ctx harness init --mode plugin
claude
# /plugin marketplace add ./
# /plugin install ctx@ctx-local
```

### Regenerate after updating ctx

```bash
ctx harness doctor          # templates_stale tells you regeneration is due
ctx harness init            # regenerates unmodified files, skips your edits
ctx harness init --force    # overwrites your edits too (rules.toml excepted)
```

### Machine-readable output

```bash
ctx harness init --json     # file actions + settings snippet in the envelope
ctx harness doctor --json   # health report (see docs/json-output.md)
```
